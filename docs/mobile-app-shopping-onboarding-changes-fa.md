# راهنمای تغییرات اپلیکیشن: سبد خرید، Onboarding و اصلاح مراحل عضویت

## هدف سند

اپلیکیشن از قبل پیاده‌سازی شده است. این سند برای اعمال قابلیت‌ها و اصلاحات جدید روی نسخه موجود نوشته شده و راهنمای ساخت یک اپ جدید نیست.

تغییرات اصلی عبارت‌اند از:

1. اضافه‌کردن سبد خرید هوشمند به صفحه مشاهده رژیم.
2. اضافه‌کردن صفحه Onboarding به انتهای مراحل اولیه عضویت.
3. دریافت سؤال‌ها و گزینه‌های جدید عضویت از API.
4. تغییر رابط انتخاب سرعت کاهش وزن از اسکرول افقی به گزینه‌های مشخص.
5. رفع باگ‌های مسیریابی دستور پخت، ثبت مقدار اعشاری غذا، دوره دوم ۱۵ روزه، وعده‌های ورزشی و Popup رژیم.

Swagger قابلیت‌های جدید در آدرس زیر در دسترس است:

```text
GET /docs/shopping-list
```

تمام endpointهای این سند با پیشوند `/v1` و Bearer Token مربوط به Laravel Sanctum فراخوانی می‌شوند، مگر Login و Verify که عمومی هستند.

## ۱. ترتیب کلی ورود و مراحل عضویت

### رفتار مورد انتظار

پس از Verify یا تکمیل اطلاعات ثبت‌نام، اپ نباید مسیر بعدی را خودش حدس بزند. مسیر فقط از این فیلدهای API تعیین شود:

```json
{
  "show_onboarding": true,
  "next_route": "/onboarding",
  "user_status": "/onboarding"
}
```

ترتیب تصمیم‌گیری:

```text
ورود/تأیید کد
  ├─ next_route = /statement  → ادامه مراحل عضویت
  ├─ next_route = /onboarding → نمایش Onboarding
  └─ next_route = /profile    → ورود مستقیم به اپ
```

معنای مسیرها:

- `/statement`: اطلاعات اولیه کاربر هنوز کامل نشده است.
- `/onboarding`: Onboarding در پنل فعال است و کاربر پکیج فعال ندارد.
- `/profile`: Onboarding غیرفعال است یا کاربر از قبل عضویت فعال دارد.

این تصمیم در پاسخ‌های Verify، ثبت Device و `complete_register` موجود است.

## ۲. سؤال‌ها و تغییرات مراحل عضویت

### دریافت سؤال‌ها از API

```http
GET /v1/registration/questions
Authorization: Bearer {token}
Accept: application/json
```

سؤال‌ها همچنین در پاسخ Verify و ثبت Device داخل `registration_questions` برمی‌گردند. اگر همان پاسخ در دسترس است، درخواست جداگانه لازم نیست.

ساختار هر سؤال:

```json
{
  "key": "food_budget",
  "type": "single_choice",
  "required": true,
  "title": "دوست داری برنامه غذاییت از نظر هزینه چطور باشه؟",
  "options": [
    { "value": 0, "title": "اقتصادی و به‌صرفه" }
  ]
}
```

اپ باید بر اساس `key` مقدار انتخابی را در `statement` ارسال کند. برای نمایش متن گزینه‌ها از پاسخ API استفاده شود و مقدار نمایشی به‌عنوان مقدار API ارسال نشود.

### ۲.۱ تغییر صفحه شرایط غذایی

متن قبلی در اپ:

```text
آیا محدودیتی در مصرف غذا داری؟
```

متن جدید:

```text
آیا رژیم غذاییت شرایط خاصی داره؟
```

این عنوان تغییر رابط کاربری اپ است و نیازی نیست از API خوانده شود.

در همان صفحه، گزینه زیر نیز اضافه شود:

```text
از داروهای کاهش وزن استفاده می‌کنم
```

قرارداد API این گزینه:

```text
key: weight_loss_medication
0: استفاده نمی‌کنم
1: از داروهای کاهش وزن استفاده می‌کنم
```

اگر این گزینه به‌شکل Checkbox نمایش داده می‌شود:

- Checkbox انتخاب‌شده: `weight_loss_medication = 1`
- Checkbox انتخاب‌نشده: `weight_loss_medication = 0`

### ۲.۲ سؤال هزینه برنامه غذایی

این سؤال به مراحل عضویت اضافه شود:

```text
دوست داری برنامه غذاییت از نظر هزینه چطور باشه؟
```

گزینه‌ها:

| value | عنوان |
|---:|---|
| `0` | اقتصادی و به‌صرفه |
| `1` | متعادل و متنوع |
| `2` | هزینه برام مهم نیست |

نام فیلد ارسالی:

```text
food_budget
```

### ۲.۳ تغییر انتخاب سرعت کاهش/تغییر وزن

در صفحه «بزن بریم، رژیم شما آماده‌ست»، انتخاب سرعت تغییر وزن از حالت اسکرول چپ و راست خارج شود.

زیر نمودار این سؤال نمایش داده شود:

```text
دوست داری هر هفته چقدر وزنت تغییر کنه؟
```

سه گزینه به‌شکل Card، Radio یا Selectable Option نمایش داده شوند:

#### گزینه ۱ — استاندارد

```text
حدود ۵۰۰ گرم در هفته
آرام و قابل ادامه
```

مقدار API:

```text
weight_change_per_week = 0
```

#### گزینه ۲ — سریع‌تر

```text
۵۰۰ گرم تا ۱ کیلو در هفته
با سرعت بیشتری به هدفم برسم
```

مقدار API:

```text
weight_change_per_week = 1
```

#### گزینه ۳ — خیلی سریع

```text
بیشتر از ۱ کیلو در هفته
می‌خوام زودتر نتیجه بگیرم
```

مقدار API:

```text
weight_change_per_week = 2
```

عنوان، subtitle و description هر گزینه در پاسخ سؤال‌ها موجود است.

### ارسال پاسخ سؤال‌ها

سه مقدار باید همراه سایر اطلاعات داخل JSON فیلد `statement` در endpoint تکمیل ثبت‌نام ارسال شوند:

```http
POST /v1/complete_register
Authorization: Bearer {token}
```

نمونه محتوای `statement`:

```json
{
  "first_name": "سارا",
  "weight_loss_medication": 1,
  "food_budget": 0,
  "weight_change_per_week": 1
}
```

مقادیر خارج از بازه‌های اعلام‌شده معتبر نیستند. برای سازگاری با نسخه‌های قبلی، Backend در زمان گذار نبودن فیلدهای جدید را تحمل می‌کند؛ بااین‌حال نسخه جدید اپ باید هر سه سؤال `required` را تکمیل کند.

## ۳. Onboarding

### محل نمایش

Onboarding بعد از تکمیل موفق مراحل اولیه عضویت و قبل از ورود به Profile قرار می‌گیرد.

پس از `complete_register`:

1. پاسخ API خوانده شود.
2. اگر `show_onboarding = true` یا `next_route = /onboarding` بود، صفحه Onboarding باز شود.
3. اگر `next_route = /profile` بود، مستقیماً Profile باز شود.
4. اپ نباید Onboarding را به‌صورت hard-code برای همه کاربران نمایش دهد.

### دریافت محتوا

```http
GET /v1/onboarding
Authorization: Bearer {token}
```

نمونه پاسخ:

```json
{
  "show_onboarding": true,
  "next_route": "/onboarding",
  "mode": "free_package",
  "content": {
    "title": "سارا جان، خوش اومدی!",
    "primary_button": "۷ روز رایگان رو فعال کن",
    "secondary_button": "فعلاً نه، ادامه می‌دم"
  },
  "offer": {
    "package_id": 4,
    "name": "پکیج آزمایشی",
    "days": 7,
    "already_claimed": false
  }
}
```

### حالت‌های Onboarding

| mode | رفتار اپ |
|---|---|
| `coupon` | نمایش کد تخفیف و محتوای برگشتی |
| `free_package` | نمایش پیشنهاد پکیج رایگان و دکمه فعال‌سازی |
| `none` | نمایش محتوای معرفی بدون پیشنهاد مالی |
| `null` | Onboarding نمایش داده نشود |

تمام متن‌ها از `content` خوانده شوند؛ متن دکمه‌ها یا تعداد روزها در اپ hard-code نشود.

### فعال‌سازی پکیج رایگان

فقط در حالت `free_package`:

```http
POST /v1/onboarding/free-package/activate
Authorization: Bearer {token}
```

پاسخ موفق `201`:

```json
{
  "message": "پکیج رایگان با موفقیت فعال شد.",
  "next_route": "/profile",
  "package": {
    "package_user_id": 10,
    "package_id": 4,
    "start_at": "2026-09-24",
    "end_at": "2026-10-01"
  }
}
```

برای جلوگیری از درخواست تکراری، هنگام ارسال دکمه غیرفعال شود. اگر `already_claimed = true` است، دوباره درخواست فعال‌سازی ارسال نشود.

دکمه ثانویه Onboarding درخواست فعال‌سازی ندارد و کاربر را به Profile هدایت می‌کند.

### معیار پذیرش Onboarding

- Onboarding غیرفعال: صفحه نمایش داده نشود.
- کاربر دارای پکیج فعال: صفحه نمایش داده نشود.
- ثبت‌نام ناقص: کاربر به `/statement` برگردد.
- Onboarding فعال و کاربر بدون پکیج: صفحه نمایش داده شود.
- محتوا و پیشنهاد فقط از API خوانده شوند.

## ۴. سبد خرید هوشمند چیست؟

سبد خرید هوشمند، مواد لازم رژیم کاربر را برای «فردا» یا «هفت روز آینده» از وعده‌های تجویزشده استخراج می‌کند. غذاهای ترکیبی به اقلام قابل خرید تبدیل و اقلام یکسان تجمیع می‌شوند.

هر قلم شامل این اطلاعات است:

- نام ماده غذایی؛
- مقدار و واحد؛
- متن قابل نمایش مقدار؛
- تخمینی‌بودن مقدار؛
- وضعیت خرید/تیک؛
- وعده‌ها و تاریخ‌هایی که باعث اضافه‌شدن قلم شده‌اند.

ساخت سبد با AI و به‌صورت Job انجام می‌شود؛ بنابراین پاسخ درخواست ساخت ممکن است فوراً نتیجه نهایی نداشته باشد.

## ۵. محل نمایش سبد خرید

آیکن سبد خرید فقط در صفحه «مشاهده رژیم» اضافه شود.

پاسخ API مشاهده رژیم شامل این قسمت است:

```json
{
  "shopping_list": {
    "active": true,
    "icon_url": "https://api.example.com/storage/settings/icons/cart.png"
  }
}
```

قانون نمایش:

```text
اگر shopping_list.active == true:
    آیکن با shopping_list.icon_url نمایش داده شود
در غیر این صورت:
    آیکن و ورودی سبد خرید کاملاً مخفی باشد
```

Backend مقدار `active` را فقط زمانی `true` می‌کند که:

1. قابلیت سبد خرید در تنظیمات اپ فعال باشد؛
2. رژیم کاربر فعال باشد؛
3. وضعیت رژیم `ACTIVE` باشد.

اپ نباید صرفاً بر اساس وجود رژیم یا وجود `icon_url` قابلیت را فعال کند. مرجع نهایی فقط `shopping_list.active` است.

## ۶. جریان کامل ساخت سبد خرید

### انتخاب بازه

کاربر یکی از این دو حالت را انتخاب می‌کند:

| period | معنی |
|---|---|
| `daily` | سبد خرید فردا |
| `weekly` | سبد خرید هفت روز از فردا |

### مرحله ۱: درخواست ساخت

```http
POST /v1/diet/{dietRequest}/shopping-list/generate
Authorization: Bearer {token}
Content-Type: application/json
```

Body:

```json
{
  "period": "daily"
}
```

پاسخ‌ها:

- `200`: سبد با همین ورودی قبلاً آماده بوده است.
- `202`: درخواست در صف یا در حال پردازش است.
- `400`: رژیم فعال نیست یا عملیات با وضعیت فعلی ممکن نیست.
- `404`: رژیم متعلق به کاربر نیست.
- `422`: مقدار period نامعتبر است.
- `429`: درخواست‌های ساخت بیش از حد مجاز است.

نمونه پاسخ اولیه:

```json
{
  "status": "pending",
  "shopping_list_id": 42,
  "uuid": "018f...",
  "period": "daily",
  "start_date": "2026-09-25",
  "end_date": "2026-09-25",
  "message": "درخواست ساخت سبد خرید در صف پردازش است.",
  "result": null
}
```

`shopping_list_id` ذخیره شود؛ برای دریافت نتیجه، Retry و تیک‌زدن اقلام لازم است.

### مرحله ۲: وضعیت انتظار

وضعیت‌های ممکن:

| status | رفتار اپ |
|---|---|
| `pending` | نمایش «در صف پردازش» |
| `processing` | نمایش Loading و «در حال محاسبه» |
| `ready` | توقف Loading و نمایش `result` |
| `failed` | نمایش خطا و دکمه تلاش مجدد |

در حالت `pending` و `processing` دکمه ساخت مجدد غیرفعال باشد تا درخواست تکراری ایجاد نشود.

### مرحله ۳: دریافت نتیجه با Pusher

اپ روی کانال خصوصی زیر Subscribe شود:

```text
private-users.{userId}.shopping-list
```

احراز هویت کانال:

```http
POST /broadcasting/auth
Authorization: Bearer {sanctum_token}
Accept: application/json
```

رویدادها:

```text
shopping-list.processing
shopping-list.ready
shopping-list.failed
```

Payload نمونه:

```json
{
  "shopping_list_id": 42,
  "diet_request_id": 324,
  "period": "daily",
  "status": "ready",
  "message": "سبد خرید شما آماده شد."
}
```

فقط رویدادی پردازش شود که `diet_request_id` و `shopping_list_id` آن با صفحه فعلی مطابقت دارد.

پس از دریافت `shopping-list.ready`، جزئیات کامل با endpoint مشاهده دریافت شود؛ Payload وب‌سوکت فقط اعلان وضعیت است و نتیجه کامل سبد نیست.

### Polling به‌عنوان fallback

حتی با Pusher، Polling حفظ شود:

- هر ۳ ثانیه وضعیت سبد بررسی شود؛
- با `ready` یا `failed` متوقف شود؛
- هنگام خروج از صفحه Timer لغو شود؛
- پس از حدود ۲ دقیقه Timeout مناسب نشان داده شود؛
- قطع WebSocket نباید کاربر را برای همیشه در Loading نگه دارد.

## ۷. تمام APIهای سبد خرید در Swagger

### ۷.۱ ساخت یا دریافت درخواست جاری

```http
POST /v1/diet/{dietRequest}/shopping-list/generate
```

برای شروع ساخت استفاده می‌شود. Backend برای ورودی یکسان سبد تکراری تولید نمی‌کند و رکورد جاری را برمی‌گرداند.

### ۷.۲ دریافت سبد جاری براساس بازه

```http
GET /v1/diet/{dietRequest}/shopping-list?period=daily
```

یا:

```http
GET /v1/diet/{dietRequest}/shopping-list?period=weekly
```

کاربرد:

- بازیابی وضعیت پس از بازشدن دوباره صفحه؛
- Polling بدون نگهداری شناسه؛
- فهمیدن اینکه برای ورودی فعلی سبدی ساخته شده یا نه.

`404` یعنی برای بازه و نسخه فعلی رژیم هنوز سبدی وجود ندارد؛ در این حالت UI ساخت نمایش داده شود.

### ۷.۳ دریافت سبد با شناسه

```http
GET /v1/diet/{dietRequest}/shopping-list/{shoppingList}
```

کاربرد:

- دریافت نتیجه بعد از رویداد Pusher؛
- Polling با `shopping_list_id`؛
- Refresh جزئیات پس از Retry.

### ۷.۴ تیک‌زدن یا برداشتن تیک قلم

```http
PATCH /v1/diet/{dietRequest}/shopping-list/{shoppingList}/check
Content-Type: application/json
```

Body:

```json
{
  "item_key": "chicken-200g",
  "is_checked": true
}
```

نکات:

- `item_key` از `result.groups[].items[].key` گرفته شود.
- برای برداشتن تیک، `is_checked = false` ارسال شود.
- پاسخ شامل نسخه به‌روزشده کامل سبد است.
- Optimistic UI مجاز است، اما در صورت خطا وضعیت قبلی بازگردانده شود.

### ۷.۵ تلاش مجدد

```http
POST /v1/diet/{dietRequest}/shopping-list/{shoppingList}/retry
```

فقط وقتی `status = failed` فراخوانی شود. پاسخ `202` است و وضعیت دوباره به `pending` می‌رود. سپس چرخه Pusher/Polling از نو شروع شود.

### ساختار نتیجه آماده

```json
{
  "status": "ready",
  "shopping_list_id": 42,
  "period": "daily",
  "result": {
    "schema_version": 1,
    "engine": "openai",
    "title": "سبد خرید فردا",
    "total_items": 2,
    "checked_items": 0,
    "progress_percent": 0,
    "groups": [
      {
        "key": "dairy",
        "title": "لبنیات",
        "items": [
          {
            "key": "milk-1",
            "name": "شیر",
            "quantity": 1,
            "unit": "لیتر",
            "display_quantity": "حدود ۱ لیتر",
            "is_estimated": true,
            "is_checked": false,
            "sources": [
              {
                "date": "2026-09-25",
                "meal": "صبحانه",
```

گروه‌های معتبر:


## ۸. اصلاح باگ‌های نسخه فعلی اپ

### ۸.۱ بازگشت از دستور پخت

مشکل فعلی:

وقتی کاربر از یک وعده، مثلاً صبحانه، وارد دستور پخت می‌شود، با Back به صفحه کلی آشپزی می‌رود.

رفتار صحیح:

- Route مبدأ هنگام ورود به دستور پخت حفظ شود.
- Back باید به همان صفحه و همان وعده برگردد.
- مثال: `صبحانه → دستور پخت → Back → صبحانه`.
- وضعیت Scroll و روز انتخاب‌شده نیز تا حد امکان حفظ شود.
- فقط اگر صفحه دستور پخت مستقیماً از بیرون باز شده باشد، fallback می‌تواند صفحه آشپزی باشد.

معیار پذیرش:

- ورود از صبحانه، ناهار، شام و میان‌وعده جداگانه تست شود.
- Back سخت‌افزاری Android، دکمه Back داخل UI و Gesture در iOS رفتار یکسان داشته باشند.

### ۸.۲ ثبت مقدار اعشاری در افزودن غذا

مشکل فعلی:

برای مثال «شیر، نصف لیوان» قابل ثبت نیست.

رفتار صحیح:

- فیلد مقدار باید عدد اعشاری بپذیرد.
- مقدار `0.5` نباید به `0` یا `1` گرد شود.
- کیبورد ورودی باید Decimal باشد.
- مقدار اعشاری به‌صورت Number به API ارسال شود، نه Integer.
- تبدیل ارقام فارسی و ممیز فارسی قبل از ارسال انجام شود.

نمونه:

```json
{
  "quantity": 0.5
}
```

Backend محاسبات مصرف غذا را با quantity انجام می‌دهد؛ بنابراین اپ نباید مقدار را `parseInt` کند.

معیار پذیرش:

- `0.5` لیوان شیر ثبت و بعد از Refresh همان مقدار نمایش داده شود.
- مقادیر `0.25`، `0.5`، `1` و `1.5` تست شوند.

### ۸.۳ تغییر وزن و تغییر هدف در ۱۵ روز دوم

مشکل فعلی:

اپ در دوره دوم ۱۵ روزه، وزن و هدف جدید را اشتباه در نظر می‌گیرد.

رفتار صحیح:

- شروع هر دوره ۱۵ روزه باید Snapshot مستقل اطلاعات کاربر داشته باشد.
- وزن شروع دوره دوم از آخرین وزن معتبر ثبت‌شده قبل از ساخت رژیم جدید گرفته شود.
- وزن هدف از آخرین هدف ثبت‌شده کاربر گرفته شود.
- محاسبات دوره دوم نباید دوباره از وزن شروع دوره اول استفاده کنند.
- نمودار و پیشرفت دوره قبلی نباید با داده دوره جدید مخلوط شود.
- شناسه رژیم فعال، مبنای نمایش آمار، هدف و تاریخ‌ها باشد.

معیار پذیرش:

1. کاربر دوره اول را با وزن مشخص تمام کند.
2. وزن و هدف را تغییر دهد.
3. رژیم دوره دوم ساخته شود.
4. صفحه خانه، نمودار و مشاهده رژیم همگی وزن شروع و هدف جدید را نشان دهند.

### ۸.۴ وعده قبل و بعد تمرین در صفحه خانه

مشکل فعلی:

برای ورزشکار، بعد از انتخاب «امروز ورزش می‌کنم»، وعده قبل و بعد تمرین فقط در مشاهده رژیم دیده می‌شوند و در صفحه خانه نمایش داده نمی‌شوند.

رفتار صحیح:

- پس از موفقیت درخواست `set_training_day`، داده Dashboard/Home مجدداً دریافت یا invalidate شود.
- صفحه خانه و مشاهده رژیم باید از وضعیت Training Day یکسان استفاده کنند.
- وعده‌های قبل و بعد تمرین همان روز در هر دو صفحه دیده شوند.
- تغییر وضعیت نباید فقط در State محلی صفحه مشاهده رژیم باقی بماند.

معیار پذیرش:

- انتخاب «امروز ورزش می‌کنم» و بازگشت به Home بدون بستن اپ، وعده‌ها را نمایش دهد.
- بعد از بستن و بازکردن اپ نیز وعده‌ها وجود داشته باشند.

### ۸.۵ متن Popup پایان رژیم ۱۵ روزه

متن قبلی حذف و متن زیر دقیقاً جایگزین شود:

```text
رژیم ۱۵ روزه‌ات تموم شد

برای اینکه برنامه غذاییت همیشه متناسب با شرایط و وزن جدیدت باشه، هر ۱۵ روز رژیمت به‌روز می‌شه.

رژیم جدیدت کاملاً رایگانه و هیچ هزینه‌ای نداره.

ادامه بده و رژیم جدیدت رو دریافت کن
```

اپ باید Line Breakها را حفظ کند و متن را ناقص یا در یک خط نمایش ندهد.

### ۸.۶ نمایش‌ندادن Popup برای درخواست بعد از ساعت ۱۲ ظهر

مشکل فعلی:

وقتی کاربر بعد از ساعت ۱۲ ظهر درخواست رژیم می‌دهد، Popup مربوط به شروع رژیم نمایش داده نمی‌شود.

رفتار صحیح:

- شرط نمایش Popup نباید به بازه قبل از ساعت ۱۲ محدود باشد.
- زمان‌ها بر اساس timezone رسمی پروژه/کاربر محاسبه شوند، نه UTC خام دستگاه.
- پس از ثبت موفق درخواست، Dashboard باید دوباره دریافت شود تا Popup جدید خوانده شود.
- اگر API Popup را برگرداند، اپ نباید به دلیل ساعت محلی آن را فیلتر کند.
- Popup برای هر درخواست فقط یک‌بار نمایش داده شود و بعد از تأیید، endpoint ثبت وضعیت Popup فراخوانی شود.

معیار پذیرش:

- درخواست ساعت ۱۱:۵۹، ۱۲:۰۰، ۱۲:۰۱ و عصر تست شود.
- در همه حالت‌ها Popup مطابق پاسخ API نمایش داده شود.
- پس از تأیید، با Refresh دوباره نمایش داده نشود.

## ۹. مدیریت خطا و State در اپ

- همه درخواست‌ها Bearer Token داشته باشند.
- `401`: خروج امن از حساب یا Refresh فرایند احراز هویت.
- `404`: داده متعلق به کاربر نیست یا سبد جاری وجود ندارد.
- `422`: خطای ورودی در کنار فیلد مربوطه نمایش داده شود.
- `429`: دکمه موقتاً غیرفعال و پیام تلاش مجدد نمایش داده شود.
- `500`: پیام عمومی با امکان تلاش مجدد؛ جزئیات فنی به کاربر نشان داده نشود.
- هنگام خروج از صفحه، Subscription و Timerها dispose شوند.
- درخواست‌های هم‌زمان ساخت سبد، فعال‌سازی Onboarding و Retry با Double Tap ارسال نشوند.

## ۱۰. چک‌لیست تحویل نسخه اپ

- [ ] عنوان صفحه شرایط غذایی تغییر کرده است.

## ۱۱. نکته نهایی برای توسعه‌دهنده یا AI

این پروژه و اپ از قبل وجود دارند. تغییرات باید روی معماری، Navigation، State Management و Design System فعلی اعمال شوند. صفحه یا Flow موازی جدیدی که با ساختار موجود تداخل داشته باشد ساخته نشود.

مرجع حقیقت برای فعال‌بودن قابلیت‌ها Backend است:

- Onboarding: `show_onboarding` و `next_route`
- سبد خرید: `shopping_list.active`
- سؤال‌های عضویت: `registration_questions`

هیچ‌یک از این قابلیت‌ها صرفاً با Feature Flag محلی، متن hard-code یا حدس‌زدن وضعیت کاربر فعال نشوند.
